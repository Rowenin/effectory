# Artifact retention and reclamation — approved contract

Status: **approved and implemented for JSON artifacts**. The user approved revision 4, including newest-version protection, after choosing retention/reclamation before binary artifacts. Claude Effect and consumer reviews are retained alongside this contract. Binary storage limits and transport remain separate proposals.

The implementation uses Effect Duration, Schema and Clock, with durable SQLite plans, tombstones, receipts and recovery intents. The original slice provided manual CLI/RPC collection and startup cleanup recovery. **Approved amendment, 2026-11-06:** [automatic policy collection](automatic-artifact-retention-api-draft.md) adds default-off repository enable/disable/status controls, background sweeps, and continued recovery of committed cleanup. That later contract supersedes the manual-only restrictions below while preserving eligibility, newest-version protection, reader/report holds and receipt semantics. See the verification notes below for exercised behavior and remaining limits.

## Sources and constraints

Swamp has per-output lifetime and garbageCollection, explicit `data gc`, explicit version/name deletion, and repository-wide maximum-age retention. See `vendor/swamp/design/primitives/data.md`, especially Versioning and lifecycle, and `collectGarbage` in `vendor/swamp/src/infrastructure/persistence/unified_data_repository.ts`. Its per-output duration GC preserves the newest version, as does a positive count cap; the separate opt-in repository-wide age policy can remove the newest version. Its per-output GC chooses a count OR duration, rather than combining both. Version floors prevent reuse after deleting every version. Swamp also has automatic write-time/post-run collection and orphan-definition pruning. This proposal is a manual lifecycle subset with retained tombstones, not complete parity; job/workflow/ephemeral lifetimes and run-history GC remain outside it.

Effectory stores content by digest and immutable metadata/receipts in `lake_records`. Publication dedup looks up publicationKey there; version assignment uses MAX(version). Digest/length currently live in metadataJson. The same blob may back multiple versions, artifacts or principals. Run outputs, step results and event payloads may contain references. There is no general graph of references embedded in arbitrary schema values. `LakeGet` reads and verifies the content synchronously. Retention must not quietly invalidate replay receipts, reuse version numbers, unlink shared content, or break backup/restore.

## Authoring surface

```ts
const Report = Artifact.make({
  id: "report",
  version: 1,
  schema: ReportSchema,
  retention: {
    maxVersions: 10,
    maxAge: "30 days",
  },
});
```

Both fields are optional but at least one is required when retention is supplied. `maxVersions` is a positive safe integer. `maxAge` accepts Effect Duration.Input: parse with Duration.fromInput, reject non-finite values, floor to milliseconds, then require a positive safe integer of at least 1 millisecond. Invalid declarations throw synchronously using Artifact.make's existing Error convention. Reuse Duration and Schema; no custom retention builder, scheduler DSL, Context service for author code, or dependency on environment Config. Copy and freeze the normalized policy at definition construction, rather than retaining a caller-owned object via the spec spread. Omission means indefinite content retention. A policy is not part of the data schema and changing it does not require a schema version bump.

### Policy source and dormant-artifact recovery

Keep capture-at-publication semantics, paired with the bounded operator selection below. The effective policy comes from the highest-version committed row for an artifact identity, **including tombstones**. Explicitly deleting the newest content does not resurrect an older policy. Store normalized retention in a separate column outside public artifact Record metadata and the content fingerprint. Tombstoning leaves that policy column intact. An identical publication retry returns its original receipt without rewriting its captured policy.

Identity remains principal/task/output/key, not schema id. Its newest row's policy governs earlier versions even if their schema ids or schema versions differ. Two output aliases create different identities and separate version counts. Schema filters select candidate rows by each row's own schema id/version; policy selection and retained-version ranking still examine the entire identity, including retained versions outside that filter. This whole-identity ranking applies to both Policy mode and Selection keepLatest. Protected versions count toward N; tombstones do not.

Policy edits take effect on that identity's next new publication by a run pinned to a revision containing the edited definition, not merely by loading a revision. Omitting retention on that publication restores indefinite policy retention of surviving content. A long-running or retried run pinned to an older revision can publish later and temporarily restore the earlier policy, until another new-revision publication supersedes it. The highest-version row remains authoritative, independent of which revision is currently active. Loading an active registry's already-frozen policy is also technically feasible and does not require running author code; the choice here is stable captured semantics, not a claim that the active-revision alternative is impossible.

The consequence is explicit: under newest-version protection, author retention never collects single-version identities, including per-key or daily identities that had retention from the start. Operator Selection is the only collection route for them. Operators instead preview a bounded schema selection such as `lake reclaim plan --schema report --older-than "90 days"`. It uses record timestamps directly, regardless of captured policy, and may empty identities. Up to 1000 eligible versions are included in a plan; apply and repeat while hasMore. This handles legacy/dormant keys without republishing or hundreds of single-version plan/apply pairs. It is the bulk-recovery alternative proposed by the Effect reviewer and the consumer review's preferred fix.

Required focused proofs: publish v1–v3 of one identity without retention (or with maxVersions 10), tighten its definition to maxVersions 1 without republishing, and verify policy mode selects none. Publish v4 from the edited revision and verify v1–v3 become eligible. Separately create 180 daily single-version identities and verify one schema/age selection includes all eligible old versions except protected producers. Their ineligibility under Policy mode tests newest-version protection, not capture semantics. Also verify mixed-schema identity ranking, alias isolation, policy source after newest-version deletion, and unchanged captured policy on receipt replay. No active-registry policy lookup or new policy-source output field is added.

### Eligibility and newest-version protection

A non-newest version becomes eligible when older than maxAge, OR when outside the newest maxVersions. Author policies always protect the newest retained version of each artifact identity. Count only retained versions, never tombstones, ordered by immutable version number. For example, with maxVersions 3 and maxAge 30 days, versions 1–5 aged 60, 40, 35, 2 and 1 days respectively make 1–3 eligible: version 3 is among the newest three but exceeds the age limit. Versions 4 and 5 remain. If version 5 later exceeds 30 days, it remains protected while it is the newest. Removing the final version requires an explicit operator selection.

Newest-version protection is approved: a paused monthly report remains available even after maxAge passes. A daily/per-key identity with only one version also remains available. Operators can intentionally remove these through age selection, which may empty identities.

Use Clock.currentTimeMillis for evaluation time and clamp negative ages from backward clock skew to zero. Existing committedAt timestamps come from the wall clock (`new Date()`); TestClock controls evaluation time only, so tests must create appropriate fixture timestamps unless publication timestamp creation is also moved to Clock. Duration parsing accepts zero, negative and infinite values; NaN normalizes to zero, a bare number means milliseconds, and bigint means nanoseconds. The finite-positive whole-millisecond check rejects the invalid/too-small cases. Month units are unsupported; examples use days or weeks. Apply the same normalization to operator durations. Persisted policy uses maxAgeMillis, and selection RPCs use olderThanMillis, both positive safe-integer Schema.Int fields. Never encode these as DurationFromMillis, whose infinity would become JSON null, or accept arbitrary Duration objects at the RPC boundary.

Do not delete anything automatically in this first slice: authors declare eligibility, operators preview and apply reclamation. Existing artifacts without a captured policy remain indefinite under policy collection; operator selections provide bulk recovery without republishing dormant keys. A distinct daily publication key creates a distinct artifact identity, so maxVersions alone cannot clean up a year of one-version daily reports.

## Operator surface

Keep the existing `lake` CLI family. One `reclaim` plan/apply mechanism supports policy collection, bounded operator selection and explicit version removal:

```sh
effectory lake reclaim plan --policy --json
effectory lake reclaim plan --policy --schema report --schema-version 1 --json
effectory lake reclaim plan --schema report --older-than "90 days" --json
effectory lake reclaim plan --schema report --older-than "90 days" --keep-latest 2 --json
effectory lake reclaim plan --artifact <artifactId> --version 3 --json
effectory lake reclaim apply <planId> --json
```

No arbitrary filesystem paths, SQL, shell, user-defined predicates or unbounded `--all` deletion. No selection flags means captured-policy mode, equivalent to `--policy`; `--policy` cannot be mixed with operator age/count selectors or explicit artifact/version deletion. A schema-scoped age selection can reclaim dormant and legacy daily reports in batches without changing code or republishing. `lake query` and `lake versions` expose artifact ids; schema-scoped previews also provide sizing information, so no new usage command is needed. Reclamation frees space only when selected blobs have no remaining references.

Library/runtime entry points and server RPCs:

- Lake.planReclamation / `LakeReclamationPlan`: use Schema.TaggedStruct and Schema.Union with three wire variants: `{ _tag: "Policy", schemaId?, schemaVersion? }`, `{ _tag: "Selection", schemaId, schemaVersion?, artifactId?, olderThanMillis?, keepLatest? }`, or `{ _tag: "Version", artifactId, version }`. Principal comes from authentication. A schema version requires schemaId. Preview performs no deletion. CLI `--older-than` normalizes Effect Duration input to olderThanMillis before submission; the service and RPC consume that normalized schema.
- Selection requires at least one of olderThanMillis or keepLatest. keepLatest is a positive safe integer protecting the newest N retained versions of each identity. olderThanMillis selects versions strictly older than the preview's fixed cutoff; when both are supplied, select only old versions outside the protected newest N. An age-only operator selection may empty an identity. It overrides captured author policy but never unfinished-producer protection. The explicit version variant may also remove the final version. These selectors preserve the reviewed schemaId/schemaVersion/artifactId/version/olderThan/keepLatest concepts; the milliseconds wire representation adds no selector or expression language.
- Lake.applyReclamation / `LakeReclamationApply`: `{ planId }`. The actor-scoped planId is the idempotency key, with at most one application and one durable receipt per plan. No separate request key or status RPC. Repeating apply returns the current receipt and resumes pending cleanup without repeating logical deletion.

Plan output: `{ planId, expiresAt, candidates, candidateVersions, logicalBytes, reclaimableBlobBytes, protectedVersions, emptiedArtifacts, hasMore }`. Each candidate identifies artifactId/version, reason (`Age`, `VersionCount`, `Explicit`) and byte size; flag candidates that remove the final retained version, and report how many identities would become empty. An empty plan is valid and applying it is a no-op. Plans are immutable, actor-scoped, valid for 15 minutes, and contain at most 1000 candidate versions. Keep at most 64 unexpired, unapplied plans per actor; prune expired plans before rejecting a new one with LimitExceeded. CLI help documents `plan → apply → plan` while hasMore; no unbounded `--until-empty` mutation is added.

logicalBytes is the sum of the candidate records' sizes. reclaimableBlobBytes is a plan-time estimate of unique physical blobs that can be removed, not a promise; a blob still referenced outside the candidate set contributes zero. Deleting 1000 identical JSON versions can free no bytes if one retained version still references their shared content. The apply receipt's reclaimedBytes is authoritative.

Apply must look up an existing actor-scoped receipt BEFORE checking plan expiry. A request started at minute 14 and retried at minute 16 returns its receipt and resumes cleanup; it does not fail expiry after deleting data. Only a never-applied expired plan fails Conflict with guidance to preview again. Retain receipts alongside tombstones indefinitely in this slice, so retries days later remain answerable. Applied plans/receipts do not consume the unexpired-plan admission cap. This retains metadata; content reclamation does not bound SQLite growth.

Apply receipt: `{ planId, deletedVersions, reclaimedBytes, pendingBytes, skippedVersions }`. reclaimedBytes means files actually unlinked, not merely tombstoned metadata. pendingBytes means durable cleanup work remains after an I/O error or interruption. Report failure causes honestly; do not claim that a successful metadata transaction necessarily freed disk space. Repeated apply or startup recovery finishes queued unlink work without deleting new content or repeating logical deletion. Returning the current receipt on repeated apply supplies status without another RPC.

No MCP tool in this slice; CLI and direct RPC share the same implementation. Gate new clients on `lake.retention.v1`; old clients keep JSON operations and receive an existing NotFound for content intentionally collected.

The current control plane is owner-only. Physical-byte estimates can reveal whether another principal stores identical content when cross-principal dedup exists. Before adding real multi-principal access, restrict physical-byte reporting to the owner or redesign that reporting/dedup boundary; do not expose this owner-only estimate unchanged to other principals.

## Referential and replay behavior

Never collect a version produced by a run in any non-terminal status. Reuse the runtime's terminal set (currently Succeeded, Failed, Rejected, TimedOut, Cancelled), rather than maintaining a second enumerated protected list. In particular Cancelling and NeedsAttention remain protected. This protects in-flight publication receipt reuse; recheck protection inside apply's metadata transaction. Explicit version deletion obeys the same protection; no force bypass. Plan output reports protected counts and directs operators to finish/cancel the producing run, then wait for terminal settlement.

**Approved reader amendment (2026-11-06):** exact first access through ArtifactReader now records durable consumer protection, and unsettled report obligations protect their source publications. Apply re-checks both alongside unfinished producers. Inputs and query results are not scanned for references; protection starts on access and ends when the consumer is terminal. The cap is 1,024 external versions per consumer run, with same-run and protected report-source exemptions. Optional `protectedBy` plan counts and `protection` version metadata explain holds. This still does not trace arbitrary references in results/history or restore reclaimed content. See [reader usage](artifact-reads.md) and its [approved contract](artifact-reads-api-draft.md).

Preserve publication receipts and monotonic version floors after collection. Keep tombstone rows containing identity, fingerprint and reference; remove content/query projections, not historical identity. Their existing MAX(version) and uniqueness constraints preserve version floors and receipt identity. Never reuse a collected version number. A reclaimed publication receipt is unreachable through normal publish: terminal producers cannot re-enter, and non-terminal producers are protected. Keep a defensive check that a tombstoned publicationKey fails the store Conflict, mapped to the existing task PublicationConflict, with "Publication was reclaimed"; never insert a new version under the old receipt or invent a restoration path.

Queries and versions default to retained content only. Add `lake versions <artifactId> --include-reclaimed` and the corresponding optional LakeVersions request field, gated by lake.retention.v1. Included tombstones expose reclaimedAt and reclamationPlanId alongside their historical metadata, so clients distinguish deliberately reclaimed versions from never-existing versions without a new error code. `lake get` for collected content fails NotFound with an explicit reclamation message. The lake query pagination contract must detect a collection that invalidates an existing snapshot and fail CursorExpired instead of silently skipping rows. Metadata in run events remains historical; this slice does not collect events, run results or workflow journals.

Latest means newest retained version: deleting v5 makes retained v4 visible to latest queries. Exclude tombstones from the newer-row subquery as well as outer candidate rows. With all versions reclaimed, default LakeVersions returns NotFound; includeReclaimed returns the tombstones. Add a per-principal reclamationEpoch, incremented atomically when versions are tombstoned and included in both query and version cursors. A changed epoch yields CursorExpired, including when a non-anchor row was collected or an older version becomes latest. Existing anchor-only detection is insufficient. ContentUnavailable continues to indicate corruption/unavailable content, not intentional reclamation.

## Filesystem ownership and recovery

A candidate is removed only if it was eligible in the plan and remains eligible when re-evaluated inside apply's transaction. Re-evaluation uses current producer protection, the current newest-row policy (including rows committed after the snapshot and tombstones), the current retained ranking (protected versions still count), and the plan's fixed evaluation time or cutoff. Selection keepLatest is also recomputed against current retained ranking. A failed eligibility check skips and reports the candidate. Candidate identity and sequence must still match the original plan snapshot; new publications are never added to an old plan. Skip changed/ineligible candidates and report them. Concurrent new versions may make more records eligible, but require another preview. Plans exclude protected rows and order eligible candidates deterministically, so repeated plan/apply makes progress in a stable store instead of repeatedly selecting protected rows. Revalidation may still skip candidates when the store changes. The apply receipt is actor-scoped and idempotent. One SQLite transaction rechecks candidates, tombstones rows, inserts digest intents, writes the receipt and increments the reclamation epoch. No author codecs or asynchronous filesystem work run inside it.

Tombstone metadata before unlinking content. Remove a digest only when no retained record in ANY principal references it and no writer/reader lease protects it. The same physical blob is counted once. Publication installation and reclamation must coordinate through an Effect-owned store operation boundary, including the interval between blob install and record commit; do not just SELECT references and unlink later without rechecking under that boundary. Future streaming readers require a scoped read lease; today's synchronous JSON read must not race deletion either.

For today's synchronous JSON store, perform the final retained-reference recheck and unlink in one non-yielding critical section under repository ownership. The review reproduced a missing-blob corruption when cleanup yielded between those two actions and an identical publication committed. Indexed lookup of json_extract(metadataJson, '$.digest') is feasible; a partial retained-row index requires the same retained predicate in every lookup. For future asynchronous binary readers/writers, introduce internal per-digest leases acquired/released through Effect Scope, with publishers protected before the existence check and readers through stream completion. Collection skips leased digests and leaves cleanup pending; it does not block a publication waiting on a reader. No public lease API is added.

Defer inventory-based cleanup of unreferenced crash/conflict blobs; do not implicitly delete them in a plan reporting only versions, and do not add an orphan plan mode here. Cleanup intents created by this feature still recover automatically. Staging files retain their separate exclusive-owner recovery policy. Reject symlinks and unsafe filenames. Only digest-named regular files in the owned blob directory are candidates. An orphan-heavy store can still consume capacity; measure this and revisit orphan cleanup before making a binary-store recoverability guarantee.

Crash after logical deletion but before unlink leaves recoverable intents. Crash after unlink but before receipt update must be treated as completed cleanup on restart: ENOENT is success, and retained references are rechecked before every attempted unlink. A concurrent write of identical content must not lose its new blob to an old intent. Backup already copies the whole repository offline under exclusive ownership, so SQLite tombstones, receipts, version floors and cleanup intents are included automatically. The new requirement is safe, idempotent pending-intent recovery after restore. Reclamation can help meet the existing 50,000-file/1 GiB backup limits but does not bound metadata/history growth; this is content reclamation, not a total repository quota.

## Required proofs

- Definition and duration validation, including numbers, bigint nanoseconds, NaN, fractional/sub-millisecond values, infinity and unsupported months; integer wire encoding never emits null. Inference unchanged, captured policy immune to mutation; policies excluded from schema identity and publication content fingerprints.
- Count/age behavior including the worked OR example, newest-version protection, retained-only counting, operator age/count intersection, dormant daily-key bulk selection, legacy explicit deletion, and policy changes/removal.
- Plan immutability, authorization, expiry, bounds, revalidation, receipt lookup before expiry, repeated apply after partial cleanup, and useful operator errors. In particular: explicit plan A removes v5, then Policy plan B that originally selected v4 must skip v4 because it is now newest. A post-preview publication capturing a looser policy must likewise prevent obsolete policy deletion; Selection keepLatest must respect changed rankings.
- Non-terminal producer protection including Cancelling/NeedsAttention, protected rows counted in version ranking, and the documented cross-run reference limitation.
- Shared digest across artifacts/principals; concurrent publication versus collection; no version reuse or receipt corruption.
- Fault injection at metadata delete, unlink, receipt update and restore. Query and versions cursors expire on any principal reclamation epoch change, including non-anchor deletion; latest queries reveal retained v4 after v5 collection. Optional tombstone listing distinguishes reclaimed from never-existing versions.
- Reproduce the identical-content publication/unlink race, then prove the non-yielding reference check/unlink closes it. Include matching retained predicates in indexed digest lookups and idempotent ENOENT recovery.
- Effect TestClock and scoped resource tests; CLI/RPC Schema agreement and old-client compatibility.
- Planning performance at 200,000 rows, including no matches and many mixed-schema identities: the 1000-candidate output bound is not a scan bound. Prefer schema-index-driven candidates with retained-newer counts and an internal committedAtMillis column over principal-wide window ranking and repeated JSON timestamp extraction. Measure the longest synchronous lake-connection hold and total latency; use bounded scan slices with a target of at most 50 ms per slice on the recorded benchmark environment. Prove deterministic sequence ordering progresses across repeated hasMore plans without reselecting protected rows or losing eligible candidates.

The proposed binary 16 MiB size limit and storage gate are not approved by this retention decision. Reconsider those limits with actual recoverability and backup constraints before binary implementation.

## Implementation verification

Final verification on 2026-11-05: typecheck and repository formatting/lint passed, followed by 209 passing tests across 53 files (273.80 seconds). Source hashes were unchanged throughout this run.

The retained test suite covers schema/duration validation, legacy column migration, captured-policy edits and receipt replay, whole-identity ranking across schemas and output aliases, age/count OR semantics, explicit/operator selection, protected producers, 1000-candidate progress, the 64-plan cap, TestClock expiry, transaction rollback, cleanup failures before and after unlink, shared-content races, cursor invalidation and tombstone visibility. The daemon/CLI integration exercises preview/apply, offline backup/restore and replaying the same durable receipt.

A separate scratch benchmark on Darwin arm64, Bun 1.4.3 and Effect 4.0.5 populated 200,000 records from a valid publication. It distributed versions 1–3 across identities and alternated two schema IDs, sharing one small blob. With no competing verification process, a schema-filtered age preview with no matches took 833 ms; a policy preview preserving all three versions took 1428 ms; a 1000-candidate age preview took 29 ms. The largest sampled event-loop gaps were 41 ms, 7 ms and 26 ms respectively, using a 1 ms timer; the final candidate-plan transaction took 23.7 ms. These are fixture measurements, not a public latency guarantee. Seeding time is excluded.

Planning scans at most 128 raw rows before yielding through Effect. Principal/sequence and retained schema/sequence indexes avoid repeated full sorts. Newest-version checks and capped shared-digest lookups avoid constructing unnecessary identity state or counting every shared reference. The committedAtMillis column removes JSON timestamp parsing from eligibility checks. The permanent bulk test checks progress past protected rows and across repeated plans.
