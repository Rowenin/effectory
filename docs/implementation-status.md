# Implementation status

The bounded v0 library, runtime and CLI are implemented. Local verification and live public/private GitHub extension installation and offline restore checks pass. The bounded v0 roadmap is complete. See the [release checklist](release-checklist.md) for named evidence and limits.

## Working code

- The workspace installs with pinned Effect 4.0.5. Required typecheck, formatting/lint and test commands are available.
- `Task.make(spec, handler)`, canonical contracts/replacements, typed publication context, Layer-provided services and the one-attempt Task.test harness.
- `Workflow.make(spec, constructionEffect)`, schema-bound inputs, opaque references, task nodes, pure map, Boolean branches, bounded keyed fan-out, linked workflows, durable sleep, approval, typed input and signal waits. Two-stage signal registration enforces one await consumer in the same scope. Construction does not execute handlers.
- The interpreter uses Effect's persistent ClusterWorkflowEngine/SingleRunner with SQLite messages and results. Effect owns node handoffs, recorded outcomes and retry timers. Leaf handlers execute in linked native workflows so a parent wake does not replay a running manual task. Host records contain admission, attempts, wait decisions, dispatch locators, stop intents and projections; they do not duplicate the execution journal.
- One daemon owns the repository through an OS-managed SQLite exclusive lock. Manual uncertainty suspends for inspection/cancellation; it does not silently replay. This is a single-host in-process runtime, not distributed execution.
- Application source is bundled and retained by digest. The host shares canonical Effect/core module identities across revisions and keeps application service Layers scoped. New source activates on restart or a validated extension mutation; old runs retain their bundle. Candidate preparation leaves the active pointer untouched, rejects changed loaded-source inputs and stale revision candidates, and only retains successfully constructed applications. Retained bundles require their original extension digest trust decisions. Revision manifests pin a digest of host source as well as Effect version; incompatible host upgrades fail closed. A migration/upgrade path is still outstanding.
- `Extension.make`, typed `Extension.use`, lazy installed descriptors, contribution registration, explicit canonical replacements and scoped before-step patches. The compiler rejects conflicts, wrong versions/targets, missing dependencies and ordering cycles. Patch barriers use engine-owned results; input is captured once and copied independently into each patch. Workflow plans expose provider and patch selections.
- GitHub extension add/update/remove are persisted administrative operations with request-key fingerprints, registry/application revision checks and explicit local digest trust. Release resolution is checkpointed before download. Typed binding overlays let candidates validate without rewriting the live facade. A durable publication intent reconciles the lock, bindings and active pointer after process death. CLI/RPC installation, inventory/description and operation inspection are implemented. Restore remains a local bootstrap operation under exclusive ownership.
- JSON lake publication flushes content-addressed bytes before metadata/provenance/event commit. Stable publication keys deduplicate recovery. Exact reads verify digest/length. Declared JSON fields, tags and metadata support Boolean predicates, equality/ranges/membership, named projection and stable ordering. Encoded field types are recorded from schemas. Signed cursors pin principal and commit snapshots, including latest-as-of versions. Exact version history is paged. Queries bound AST size, scanned rows/bytes, elapsed work and response size without reading blobs.
- An authenticated loopback Effect RPC server and Effect CLI support definition discovery, schema descriptions, validation/planning, background submission, snapshots/events, wait inspection/answers, lake query/get and daemon start/status/drain. Repository identity and protocol version are checked. Credentials are local owner-only files.

Inspection tests cover cursor principal/filter binding, fixed admission membership, byte-limited pages, current wait settlements, and native task-result reads without re-execution. Watch tests force terminal completion after the first snapshot with more than two event batches, resume from a sequence, and release all 16 observer slots on interruption. A CLI process replays cancellation history after daemon death. Task logs/progress share a persistent bounded budget; exhaustion records one marker without blocking terminal events. RPC and task boundary tests cover byte, depth and value limits, rejecting oversized task results after a single manual attempt.

## Durable scheduling

The approved `WorkflowSchedule.make` API is implemented with immutable schema-encoded inputs and automatic workflow discovery. The owner daemon reconciles application revisions, pins each admitted run to its observed revision, and atomically persists run/outbox, occurrence history and schedule progress. Scheduled admissions use their own internal deduplication namespace while retaining normal owner visibility.

The `schedule list/get/history/pause/resume` CLI commands map to `ScheduleList/Get/History/Pause/Resume` RPCs. Get/list/watch run projections include schedule provenance. Pause survives edits, removal and re-addition; generations are never reused, and active scheduled runs block later occurrences across generations. Receipts, missed ranges, history and removed identities have explicit bounds and eviction rules. `SystemStatus.scheduler` reports the reconciled revision and state.

Focused tests verify strict encoding and input inference, service preservation, five-field cron validation, DST gaps/folds, exact-minute wakes, rollback, TestClock activation, transaction rollback after run admission, capacity retries, manual namespace isolation, waiting/NeedsAttention blockers, drain fencing, receipt eviction, protected tombstones, and cursor expiry on coalescing/pruning. A real daemon/CLI test kills and restarts an admitted waiting run, checks one occurrence and ordinary run visibility, loses a committed pause reply through a proxy, retries its printed key and completes the original run.

Runnable source: [scheduled example](../examples/scheduled/effectory.ts). Contract and known parity gaps: [approved scheduling design](scheduling-api-draft.md). Remaining Swamp scheduling gaps include advanced croner syntax, seconds fields, live source reload, a dedicated scheduled-run concurrency queue and configured run tags.

## Scheduled task context

The approved `WorkflowSchedule.Occurrence` schema is shared by run provenance, history and task fixtures. Scheduled task handlers read a fresh frozen `context.occurrence` snapshot per attempt. Manual workflows, direct task runs and default `Task.test` omit the property. `Task.test` accepts a strictly decoded optional occurrence fixture, with lazy field-specific errors. No service or Layer is required.

The scheduled example returns occurrence metadata before and after a durable approval. Tests cover fixture isolation, canonical timestamps and JSON Schema constraints, service/type preservation, inheritance through extension replacements/patches, branches and linked fan-out, retry mutation isolation, slot-based publication keys, and malformed persisted metadata. The CLI restart test compares task results across daemon death. See the [approved context contract](scheduled-task-context-api-draft.md).

## Recovery evidence

Tests cover acceptance before dispatch, competing processes, stable dispatch identity, completed activity reuse, a committed approval before engine notification, uncertain manual tasks after hard/graceful stops, short durable timers elapsed offline, suspended execution cancellation, stale lease rejection, wait validation/conflicts/expiry, cancellation races, idempotent terminal projections, publication conflicts and snapshot queries across new writes.

Deadline tests cover active task interruption, approval expiry under a shorter workflow deadline, retry backoff, attempt deadlines elapsed offline and completed-result reuse after the old deadline. Attempt start timestamps and effective ancestor deadlines are checked during admission. Retry selection retains the task’s declared error-tag types.

Operator tests also cover inactive branch captures, nested leaf limits, callback-before-trigger-return, trigger failure after an accepted callback, child error boundaries, and rejection/expiry/cancellation while a manual sibling is running. Separate process tests retain fan-out receiver IDs and result order, reuse completed manual tasks, and preserve a retry deadline while offline without repeating its recorded failed attempt.

Immediate leaf interruption uses the pinned engine's `interruptUnsafe` after persisting a stop intent. This is restricted to leaf workflows, which have no workflow compensation steps or children. Tests verify ordinary Effect resource finalizers run before terminal projection. Physical handler tracking prevents terminal projection while a handler/finalizer is still active, even if the engine has accepted interruption. After a two-second grace the run is held in NeedsAttention; interruption dispatch runs in the host scope, allowing unrelated runs to continue. A test releases an uninterruptible handler after this hold and verifies final settlement. The host caps active handlers at 32. Cancellation is not external-effect rollback, and synchronous code that blocks the JavaScript event loop still requires process-level intervention.

Positive and negative TypeScript fixtures exercise service requirements, separate canonical contracts, codec transformations and mixed references/literals with optional fields, arrays and unions. Branch/fan-out scopes and signal payload inference have type fixtures. Installed-descriptor fixtures now prove service, input and result inference. A separate-module facade fixture survives bundling and daemon death: old runs use old providers/patches while new runs use the changed revision. A publication fixture emits real `.d.mts` declarations, bundles an ESM archive, restores it into a fresh consumer, generates the facade and runs a standalone TypeScript check. Negative fixtures cover inputs, results, error tags, declared output names/value types and missing services. SDK namespace subpaths make these emitted types portable. The generated descriptor exposes additional public contract exports under `.exports`; importing its facade does not load the implementation.

Extension tests kill a process after the activation intent, lock replacement, facade replacement and active pointer write. Restart finishes the same operation; duplicate keys return its original receipt, changed payloads conflict, and stale candidates cannot overwrite newer inventory. A daemon/CLI test runs the real `gh` subprocess adapter against fixture responses: installation alone leaves application behavior unchanged, a selected update keeps an old waiting run on its old implementation, new work uses the new implementation, and removal of a required import fails without publishing its lock. Offline restore, immutable dependencies, archive corruption and local trust checks have separate tests. These fault-injection checks use fixture responses. Separate live public/private GitHub release checks now verify real downloads, publisher digests, installation, task consumption and offline restore.
